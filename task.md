You are the lead software architect and senior open-source engineer responsible for building the **Soroborno Ecosystem**.

The project is an open-source Bangla font distribution ecosystem. Its goal is to make contributing fonts extremely easy and make using those fonts effortless across modern web frameworks.

The existing project is:

* GitHub repository: `https://github.com/Taraldinn/soroborno-cdn`
* Owner: `Taraldinn`
* Existing project: Soroborno CDN

The user wants to build a **dual-repository architecture**:

1. **Font Repository:** Contains source font files and contribution-related information.
2. **Engine Repository:** Contains the processing engine, generated metadata, npm packages, framework integrations, automation, and publishing system.

The engine repository must consume and process the font repository automatically.

---

## 1. Core Product Vision

Build Soroborno as:

> **An open-source Bangla font ecosystem where contributors submit font files, and the system automatically validates, converts, generates metadata, creates CSS, updates distribution assets, and exposes the fonts across modern web frameworks.**

The contributor experience must be extremely simple.

A contributor should ideally only need to submit:

```text
fonts/<font-id>/
├── <font-file>.ttf
└── LICENSE.txt
```

Optional metadata may be supported, but contributors must not be required to manually write:

* CSS
* WOFF files
* WOFF2 files
* TypeScript definitions
* npm package code
* Framework-specific integrations
* CDN URLs
* Generated manifests

All repetitive work must be automated.

# 2. Repository Architecture

## Repository 1 — Font Repository

Existing repository:

```text
https://github.com/Taraldinn/soroborno-cdn
```

This repository should become the **source-of-truth repository for fonts**.

Its primary responsibility is to store:

* Source font files
* Licensing information
* Optional contributor metadata
* Contribution documentation

It should remain simple and contributor-friendly.

Suggested structure:

```text
soroborno-cdn/
├── fonts/
│   ├── solaiman-lipi/
│   │   ├── SolaimanLipi.ttf
│   │   └── LICENSE.txt
│   │
│   ├── kalpurush/
│   │   ├── Kalpurush.ttf
│   │   └── LICENSE.txt
│   │
│   └── <new-font>/
│       ├── <font>.ttf
│       └── LICENSE.txt
│
├── CONTRIBUTING.md
├── README.md
└── LICENSE
```

Do not assume this structure already exists. First inspect the actual repository and adapt the design to the existing implementation.

The font repository should not require contributors to edit generated files.

Avoid making contributors manually maintain:

```text
fonts.json
fonts.ts
font.css
WOFF files
WOFF2 files
npm package files
```

Those should be generated by the engine.

## Repository 2 — Engine Repository

Create or design a separate repository named:

```text
soroborno-engine
```

This repository will contain:

* Font discovery
* Font validation
* Font inspection
* Font conversion
* Metadata generation
* CSS generation
* Font registry generation
* npm packages
* Framework adapters
* Documentation
* Automated tests
* CI/CD
* Release automation

The engine must consume the font repository as an external source.

Do not duplicate the font repository manually inside the engine repository.

Use a reliable synchronization strategy such as:

* GitHub Actions checkout
* Pinned repository commit
* Configurable repository reference
* Optional Git submodule for local development

Choose the approach that provides the best reproducibility and maintainability.

The engine must not depend on a mutable branch without a reproducible reference.

# 4. Engineering Principles

Follow these principles throughout the project:

### Separation of concerns

The font repository contains source assets.

The engine repository contains processing and distribution logic.

### Single source of truth

Font metadata must be generated from the actual font files and optional contributor metadata.

Do not manually maintain duplicate font definitions across packages.

### Automation first

If a task can be derived from the font file or repository structure, automate it.

### Reproducible builds

The same font repository commit and engine version should produce the same output.

### Framework independence

The core font system must not depend on React, Vue, Next.js, Nuxt, or any other framework.

### Type safety

Use TypeScript for the npm ecosystem where appropriate.

### Open-source friendliness

Make contribution instructions simple, clear, and beginner-friendly.

### No unnecessary microservices

This is a modular monorepo-based ecosystem, not a distributed microservice system.

### No runtime dependency on GitHub

Published npm packages must not need to call GitHub APIs to discover fonts during normal application runtime.

# 5. Font Contribution Pipeline

Implement an automated pipeline:

```text
Font Repository
      │
      ▼
Detect changed fonts
      │
      ▼
Validate font files
      │
      ▼
Inspect font metadata
      │
      ▼
Validate licensing information
      │
      ▼
Detect duplicates and conflicts
      │
      ▼
Convert TTF → WOFF
      │
      ▼
Convert TTF → WOFF2
      │
      ▼
Generate normalized metadata
      │
      ▼
Generate CSS
      │
      ▼
Generate font registry
      │
      ▼
Build npm packages
      │
      ▼
Run tests
      │
      ▼
Generate preview/report
      │
      ▼
Publish after approval
```

The pipeline should provide clear errors.

Example:

```text
✓ Valid TTF file
✓ Font family detected
✓ License information found
✓ No duplicate detected
✓ WOFF generated
✓ WOFF2 generated
✓ Metadata generated
✓ CSS generated
✓ Package build passed
```

Example failure:

```text
✗ Font file is invalid
✗ License information is missing
✗ Font family conflicts with an existing font
```

Do not silently accept invalid or unlicensed fonts.

# 6. Font Metadata System

Design a normalized metadata format.

Example:

```json
{
  "id": "solaiman-lipi",
  "family": "SolaimanLipi",
  "displayName": "SolaimanLipi",
  "category": "bangla",
  "weights": [400, 700],
  "styles": ["normal"],
  "subsets": ["bengali", "latin"],
  "license": {
    "name": "OFL-1.1",
    "url": "https://scripts.sil.org/OFL"
  },
  "source": {
    "repository": "Taraldinn/soroborno-cdn"
  },
  "files": {
    "400": {
      "normal": {
        "ttf": "...",
        "woff": "...",
        "woff2": "..."
      }
    }
  }
}
```

Do not assume every font has the same metadata.

The system must handle:

* Single-weight fonts
* Multiple-weight fonts
* Regular and italic styles
* Variable fonts, if supported
* Missing optional metadata
* Different naming conventions
* Duplicate family names
* Font files with unusual filenames

Use font inspection tools to detect metadata where possible.

Allow optional contributor metadata to override or supplement automatically detected values, but validate all overrides.

# 7. Font Processing Engine

Build a dedicated processing layer.

Suggested responsibilities:

```text
engine/
├── discovery/
├── validation/
├── inspection/
├── conversion/
├── metadata/
├── css/
├── manifests/
└── pipeline/
```

The engine should support:

### Discovery

Find font files in the font repository.

### Validation

Validate file format, readability, metadata, duplicates, and licensing requirements.

### Inspection

Extract:

* Family name
* Subfamily
* Weight
* Style
* Version
* Glyph coverage
* Variable font axes, if applicable

### Conversion

Generate:

* WOFF
* WOFF2

Use established font-processing tools rather than implementing font conversion manually.

### Metadata

Generate normalized font manifests.

### CSS

Generate correct `@font-face` declarations.

### Manifests

Generate machine-readable data for npm packages and framework adapters.

# 9. Core npm Packages

Start with these packages:

```text
@soroborno/core
@soroborno/fonts
@soroborno/css
```

### `@soroborno/core`

Framework-independent APIs.

Example:

```ts
import {
  getFont,
  getFontUrl,
  getFontCss,
  listFonts,
  getFontFamily
} from "@soroborno/core";
```

Example:

```ts
const font = getFont("solaiman-lipi");
```

```ts
const css = getFontCss("solaiman-lipi", {
  weights: [400, 700]
});
```

```ts
const url = getFontUrl("solaiman-lipi", {
  weight: 400,
  style: "normal",
  format: "woff2"
});
```

The core package must have zero framework dependencies.

### `@soroborno/fonts`

Contains generated font definitions and metadata.

Example:

```ts
import { fonts, solaimanLipi } from "@soroborno/fonts";
```

### `@soroborno/css`

Provides CSS generation and optional CSS utilities.

Do not duplicate logic between `core` and `css`.

# 12. CDN Strategy

The existing Soroborno CDN infrastructure must remain usable.

The engine should generate stable CDN URLs based on the actual repository structure and configured CDN provider.

Do not hardcode URLs throughout the codebase.

Create a centralized CDN URL resolver.

Example:

```ts
getFontUrl("solaiman-lipi", {
  weight: 400,
  format: "woff2"
});
```

The URL generation system must support:

* Stable paths
* Versioning strategy
* Multiple formats
* Multiple weights
* Multiple styles
* Future CDN changes

Do not require the npm package to fetch metadata from the CDN at runtime.
